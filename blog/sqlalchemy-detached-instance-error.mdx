## 现象：断点「蒸发」了

在调试 Python 后台任务时，我遇到一个非常诡异的问题：

1. IDE 调试器正常单步执行
2. 走到某一行代码后，程序直接「消失」了
3. 没有报错，没有 traceback，日志一片平静
4. 前端看起来一切正常（因为错误被框架层吞掉了）

消失的代码行是这样的：

```python
from_account_id = conversation.from_account_id
```

上一秒还在 Redis XADD，下一秒就像什么都没发生过。

## 代码现场

简化后的代码结构：

```python
class PushMessageTool(BuiltinTool):
    def _invoke(self, user_id, tool_parameters, conversation_id=None, app_id=None):
        with Session(db.engine) as session:
            conversation = session.scalar(
                select(Conversation).where(Conversation.id == conversation_id)
            )
            
            # ... 创建 Message，commit ...
            session.commit()
            new_message_id = new_message.id

        # ← session 在这里关闭
        
        # Redis 操作（正常执行）
        redis_client.xadd(stream_key, {...})
        redis_client.expire(stream_key, 86400)

        # 然后走到这里 ↓
        from_account_id = conversation.from_account_id  # ← 断点在这里蒸发
```

## 根因分析：三幕剧

### 第一幕：expire_on_commit

SQLAlchemy `Session` 默认配置 `expire_on_commit=True`。这意味着：

> 调用 `session.commit()` 后，所有已加载的 ORM 实例会被标记为 **过期（expired）**。当你下次访问实例属性时，Session 会尝试重新从数据库加载该实例。

```python
with Session(db.engine) as session:
    conversation = session.scalar(select(Conversation).where(...))
    session.commit()  # conversation 被标记为 expired
    # 但此时 session 还活着！所以访问 conversation.xxx 仍然有效
    print(conversation.from_account_id)  # ✅ OK

# with 块结束，session 关闭
print(conversation.from_account_id)  # ❌ DetachedInstanceError!
```

### 第二幕：DetachedInstanceError

当 `with Session(...) as session:` 块结束时，Session 被关闭。此时如果访问已过期（expired）的 ORM 实例属性：

```
sqlalchemy.orm.exc.DetachedInstanceError:
  Instance <Conversation at 0x...> is not bound to a Session;
  attribute refresh operation cannot proceed
```

这个异常被抛出了，但因为是在 Generator 的 `yield` 之后发生的，它被上层框架的 generator 消费逻辑捕获并静默处理了。

### 第三幕：Generator 吞异常

为什么看不到错误？因为 `_invoke` 方法返回的是 `Generator[ToolInvokeMessage, None, None]`：

```python
def _invoke(...) -> Generator[ToolInvokeMessage, None, None]:
    # ... 前面的 yield 都正常返回了 ...
    yield self.create_text_message(f"Message pushed.")  # ← 成功 yield
    yield self.create_variable_message("message_id", new_message_id)  # ← 这一行永远不会执行
```

当 DetachedInstanceError 在 `yield` 之间抛出时，框架的 generator 驱动代码可能将其视为 generator 终止信号，而不是 fatal error。于是：
- 流程中断
- 但后续 `yield` 不会产生任何输出
- 错误被悄悄吞掉

## 修复：expire_on_commit=False

解决方案非常简单，且是项目中的标准做法：

```python
# 修改前
with Session(db.engine) as session:

# 修改后
with Session(db.engine, expire_on_commit=False) as session:
```

`expire_on_commit=False` 告诉 SQLAlchemy：**commit 后不要过期实例，保持内存中的属性值。**这样即使 session 关闭，对象仍然是 detached 但「 warm 」状态，可以安全访问属性。

## 为什么这是项目中的标准做法

在代码库中搜索 `expire_on_commit=False`，会发现它被广泛使用：

- `controllers/web/wraps.py`
- `core/tools/tool_file_manager.py`
- `models/account.py`
- `core/app/apps/workflow/app_generator.py`
- `commands.py`

这些场景的共同点是：**需要在 commit 之后继续使用 ORM 对象的属性**。这就是 `expire_on_commit=False` 的设计用途。

## 更深层的反思

### 1. 为什么这不是默认行为？

SQLAlchemy 默认 `expire_on_commit=True` 是为了保证 **数据一致性**。假设：

```python
with Session(db.engine) as session:
    user = session.get(User, 1)
    session.commit()
    # 如果其他事务修改了 user 的数据...
    print(user.name)  # expire_on_commit=True 会重新加载最新值
```

默认行为确保你不会读到 stale 数据。但代价是 session 必须保持打开，或者重新查询。

### 2. 什么时候应该用 `expire_on_commit=True`？

- 长事务场景，commit 后可能间隔很久才访问属性
- 多用户并发修改同一行的场景
- 需要确保读取最新数据的报表/统计逻辑

### 3. 更安全的写法

如果必须在 session 外使用 ORM 对象，更好的做法是在 session 内提取需要的值：

```python
with Session(db.engine) as session:
    conversation = session.scalar(select(Conversation).where(...))
    from_account_id = conversation.from_account_id  # ← 在 session 内提取
    session.commit()

# session 外安全使用 from_account_id
redis_client.xadd(...)
```

或者使用 `selectinload` / `joinedload` 提前加载关联对象，避免 lazy loading 在 session 外触发。

## 总结

| 现象 | 原因 | 修复 |
|------|------|------|
| 断点执行到某行后「消失」 | DetachedInstanceError 被 Generator 吞掉 | `Session(..., expire_on_commit=False)` |
| 没有错误日志 | 异常在 generator 中间抛出，被框架层静默处理 | 在 session 内提前提取需要的属性值 |
| 流程看似正常但实际中断 | Redis 操作已完成，但后续代码未执行 | 遵循项目中 `expire_on_commit=False` 的标准做法 |
