## 工具系统整体架构

### 核心接口

**`packages/opencode/src/tool/tool.ts`**

```typescript
// 工具定义接口
interface Def<Parameters, Metadata> {
  id: string
  description: string
  parameters: Parameters          // Effect Schema，用于参数验证
  execute(args, ctx: Context): Effect<ExecuteResult<Metadata>>
}

// 工具上下文（每次调用时注入）
type Context = {
  sessionID: SessionID
  messageID: MessageID
  agent: string
  abort: AbortSignal
  callID?: string
  messages: MessageV2.WithParts[]
  metadata(input): Effect<void>   // 更新 UI 显示的 title/metadata
  ask(input): Effect<void>        // 触发权限审批
}
```

`Tool.define()` 是工厂函数，接受工具 ID 和一个 Effect，Effect 内部可以 yield 依赖的服务。

### 工具绑定到 LLM（tools.ts）

**`packages/opencode/src/session/tools.ts`**

在每次 chat 请求时，`SessionTools.resolve()` 将 `Tool.Def[]` 转换为 Vercel AI SDK 格式：

```typescript
tools[item.id] = tool({
  description: item.description,
  inputSchema: jsonSchema(schema),
  execute(args, options) {
    return run.promise(
      Effect.gen(function* () {
        const ctx = context(args, options)     // 构建 Tool.Context
        yield* plugin.trigger("tool.execute.before", ...)
        const result = yield* item.execute(args, ctx)   // ← 实际执行工具
        yield* plugin.trigger("tool.execute.after", ...)
        return result
      })
    )
  }
})
```

<Callout type="info">
  `EffectBridge.make()` 将 Effect fiber 桥接到 Promise（Vercel AI SDK 需要 Promise）。`permission.ask()` 是一个阻塞 Effect，会挂起直到用户审批。
</Callout>

## Question 工具深度解析

### 工具定义层

**`packages/opencode/src/tool/question.ts`**

```typescript
export const QuestionTool = Tool.define<typeof Parameters, Metadata, Question.Service>(
  "question",
  Effect.gen(function* () {
    const question = yield* Question.Service  // ← DI 注入问答服务

    return {
      description: DESCRIPTION,
      parameters: Parameters,   // Schema: { questions: QuestionPrompt[] }
      execute: (params, ctx) =>
        Effect.gen(function* () {
          // ① 调用 Question.Service.ask()，阻塞当前 fiber
          const answers = yield* question.ask({
            sessionID: ctx.sessionID,
            questions: params.questions,
            tool: ctx.callID
              ? { messageID: ctx.messageID, callID: ctx.callID }
              : undefined,
          })

          // ② answers 收到后，格式化返回给 LLM
          const formatted = params.questions
            .map((q, i) => `"${q.question}"="${answers[i]?.join(", ") || "Unanswered"}"`)
            .join(", ")

          return {
            title: `Asked ${params.questions.length} question(s)`,
            output: `User has answered your questions: ${formatted}. You can now continue.`,
            metadata: { answers },
          }
        })
    }
  })
)
```

### 问答服务层（核心 Deferred 机制）

**`packages/opencode/src/question/index.ts`**

这是整个 question 工具的核心——使用 Effect `Deferred` 实现异步挂起/恢复。

```typescript
// State: 维护所有待回答的问题
interface State {
  pending: Map<QuestionID, {
    info: Request
    deferred: Deferred<ReadonlyArray<Answer>, RejectedError>
  }>
}
```

**`ask()` 方法流程：**

```typescript
const ask = function* (input: { sessionID, questions, tool? }) {
  const id = QuestionID.ascending()       // ① 生成唯一 ID
  const deferred = yield* Deferred.make() // ② 创建 Deferred（类似 Promise）

  pending.set(id, { info, deferred })     // ③ 存入 pending Map

  yield* bus.publish(Event.Asked, info)   // ④ 发布事件，触发前端显示

  // ⑤ 阻塞等待用户回答——Deferred.await 挂起当前 fiber
  return yield* Effect.ensuring(
    Deferred.await(deferred),
    Effect.sync(() => { pending.delete(id) })  // 清理
  )
}
```

**`reply()` 方法流程：**

```typescript
const reply = function* (input: { requestID, answers }) {
  const existing = pending.get(input.requestID)
  pending.delete(input.requestID)

  yield* bus.publish(Event.Replied, { sessionID, requestID, answers })

  yield* Deferred.succeed(existing.deferred, input.answers)  // ← 恢复被挂起的 fiber！
}
```

<Callout type="warning">
  **关键洞察**：`Deferred.await(deferred)` 和 `Deferred.succeed(deferred, answers)` 是跨 Effect fiber 的同步点。LLM 工具调用的 fiber 被挂起，直到用户通过 HTTP API 调用 `reply`，才会恢复执行并将答案返回给 LLM。
</Callout>

```

    │
    ▼

    │
    ▼

    │
    ▼
bus.publish(Event.Replied)            ← SSE 通知前端移除 Question UI
```

## Permission 与 Question 的对比

Permission（权限审批）与 Question（用户问答）共享相同的架构模式：

| 方面 | Question | Permission |
|------|----------|------------|
| 触发时机 | LLM 主动调用 `question` 工具 | 工具执行前的权限检查 |
| 挂起机制 | `Deferred.await()` | `Deferred.await()` |
| 事件 | `question.asked/replied/rejected` | `permission.asked/replied` |
| UI 组件 | `SessionQuestionDock` | `SessionPermissionDock` |
| 回复端点 | `PUT /question/:id/reply` | `PUT /permission/:id/respond` |
| 拒绝行为 | `RejectedError` → 工具返回错误给 LLM | `RejectedError` → 工具执行中断 |

## 关键设计模式总结

<CardGroup cols={2}>
  <Card title="Effect Deferred 作为异步门" icon="door-open">
    Question 和 Permission 都用 `Deferred` 将"等待外部输入"建模为 Effect，支持类型化错误（`RejectedError`），比传统回调/Promise 链更简洁。
  </Card>
  <Card title="事件驱动的 UI 同步" icon="arrows-rotate">

  </Card>
  <Card title="乐观更新" icon="bolt">

### Permission 与 Question 的流水线优先级

`session-composer-state.ts` 的 `blocked()` 信号：

```typescript
const blocked = createMemo(() => !!permissionRequest() || !!questionRequest())
```

只要有 permission 或 question 待处理，输入框就隐藏（`showComposer = !blocked || child`）。两者不会同时显示，优先显示先到达的请求。
