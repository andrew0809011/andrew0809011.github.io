## 现象：rolling patch 期间定时「断连」

DBA 团队通知对生产 MySQL 集群做滚动补丁。理论上主从切换 + VIP 漂移是透明的，应用层不应该有感知。但实际监控显示，补丁窗口内每隔几十秒就有请求失败：

```
sqlalchemy.exc.OperationalError: (pymysql.err.OperationalError) (2013, 'Lost connection to MySQL server during query')
```

错误集中在补丁节点切换的瞬间。DBA 确认 DB 侧主从切换和 VIP failover 都正常，问题出在应用侧。

## 现有配置：pool_pre_ping 已经开了

检查应用的数据库连接配置：

```python
# 已有的连接池配置
SQLALCHEMY_POOL_PRE_PING = True   # ✅ 已开启
SQLALCHEMY_POOL_TIMEOUT = 30      # ✅ 合理
# SQLALCHEMY_POOL_RECYCLE 未设置 → 默认 3600s  ❌ 太长
```

`pool_pre_ping=True` 意味着 SQLAlchemy 在借出连接前会先发一条 `SELECT 1` 验证连接是否存活。这已经是一道防线了，为什么还会报 2013？

## 根因：pool_pre_ping 救不了「在途」查询

`pool_pre_ping` 的工作时机是**借出连接之前**，它只能检测「连接在池子里就已经死了」的情况：

```
请求进入 → 从池中借出连接 → pool_pre_ping SELECT 1 → OK ✅
         → 开始执行业务查询...
         → 🔴 MySQL 主库在这个瞬间重启
         → 2013: Lost connection during query 💥
```

**pool_pre_ping 管不了正在执行的查询。** 这就是 rolling patch 场景下的问题：

1. 连接借出时 ping 通过了
2. 查询执行到一半，对应的 MySQL 节点重启
3. 连接断开，抛出 2013
4. 即使 VIP 已经漂移到新主，池里的旧连接仍然指向旧主

再加上 `pool_recycle` 默认 3600s（1 小时），这些指向旧主的连接要等很久才会被自然淘汰。

## 方案：两层防护

### 第一层：缩短 pool_recycle

先把连接最大存活时间从 1 小时降到合理值：

```
SQLALCHEMY_POOL_RECYCLE = 600  # 10 分钟
```

这样 failover 后旧连接最多存活 10 分钟就会被回收，新建立的连接通过 VIP 会自然地指向新主。

但这只是「加速淘汰」，真正的问题是——**在查询执行中遇到断连怎么办？**

### 第二层：Engine 级别的自动重试

SQLAlchemy 提供了 `handle_error` 事件，可以在 Engine 层面拦截异常并决定是否重试：

```python
from sqlalchemy import event
from sqlalchemy.engine import Engine
from sqlalchemy.exc import OperationalError

# 需要重试的 MySQL 错误码
# 2006: MySQL server has gone away
# 2013: Lost connection to MySQL server during query
_RETRYABLE_MYSQL_ERRORS = (2006, 2013)


def setup_engine_retry():
    @event.listens_for(Engine, "handle_error")
    def _handle_db_error(exception_context):
        # 只处理 OperationalError
        if not isinstance(exception_context.original_exception, OperationalError):
            return

        # 检查错误码是否在重试白名单里
        orig = exception_context.original_exception
        error_code = orig.args[0] if orig.args else None
        if error_code not in _RETRYABLE_MYSQL_ERRORS:
            return

        # invalidate 旧连接，下次重试时会从池中取新连接（通过 VIP 指向新主）
        try:
            exception_context.connection.invalidate()
        except Exception:
            pass

        # 告诉 SQLAlchemy：这个操作可以重试
        exception_context.retryable = True
```

关键点：

- **`exception_context.connection.invalidate()`** — 把当前这个已经断掉的连接标记为无效，SQLAlchemy 重试时会创建新连接
- **`exception_context.retryable = True`** — 告诉 SQLAlchemy 框架层"这个异常是可恢复的，请重试"
- SQLAlchemy 内部会自动处理重试次数和退避策略，不需要手动实现

### 注册到应用初始化流程

```python
def init_app(app):
    db.init_app(app)
    setup_engine_retry()  # ← 新增
    # ...
```

## 完整防护链

修复后的请求流程：

```
请求进入 → 借出连接 → pool_pre_ping ✅ → 执行查询中
         → MySQL 主库重启 → 2013 错误
         → handle_error 捕获 → invalidate 旧连接
         → SQLAlchemy 自动重试 → 新连接走 VIP → 新主 ✅
```

配合 `pool_recycle=600`，即使有些连接在池子里悄悄过期（没被借出、没触发 ping），也会在 10 分钟内被回收。

## 总结

| 机制 | 解决的问题 | 覆盖不到的场景 |
|------|-----------|--------------|
| `pool_pre_ping` | 借出前发现死连接 | 查询执行中连接断开 |
| `handle_error` 重试 | 查询执行中连接断开 | 非 MySQL 错误、非连接类错误 |
| `pool_recycle` | 池中僵尸连接自然淘汰 | 回收窗口内的瞬间故障 |

三者互补，缺一不可。这个方案完全在应用层实现，不依赖外部中间件，对业务代码零侵入。
